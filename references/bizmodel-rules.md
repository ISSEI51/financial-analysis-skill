# ビジネスモデル図のルール

企業・顧客・取引先などの主体をアイコンで表し、商品・サービス、お金、情報などの流れを矢印で表した図を作る。
図は `bizmodel.py` が **ビジネスモデル JSON** から生成する。手で図形を描いたり、画像生成 AI で代替したりしない。
すべての決算分析で作る（必須）。生成に失敗した場合は原因が記録され、財務分析は続行できる（下の「失敗したとき」）。

## 1. 情報の集め方と根拠

使う資料（優先順）：

1. 有価証券報告書の「事業の内容」と「事業系統図」（主体と取引関係が最もまとまっている）、「主要な顧客」「仕入先」の記載
2. 決算説明資料・中期経営計画（サービスの説明、収益モデル、料金体系、販売経路、KPI）
3. 企業公式サイトのサービス紹介・会社概要（料金体系、提供経路、提携先）
4. 決算短信の「経営成績等の概況」「セグメント情報」

抽出する項目：商品・サービス、顧客と顧客セグメント、主要な仕入先・パートナー・販売代理店、収益源と料金体系、
サービスの提供経路、重要な情報・データの流れ、主要な事業セグメント、各取引関係を確認した出典。

守ること：

- **資料で確認できた主体と関係だけを書く。** 業種の一般的な形から関係を補わない。
- 個別の取引先名が資料にない場合は「仕入先」「販売代理店」「法人顧客」などの一般名称にする。ただし、その主体が存在することは資料で確認する（主体にも `source` が必須）。
- 関係ごとに根拠の強さを `evidence_level` で区別する。
  - `fact`（事実）：資料に関係そのものが書かれている（例：「販売代理店を通じて販売」）。
  - `interpretation`（解釈）：資料の記載から直接導ける（例：「月額課金」の記載 → 顧客から当社への利用料）。導いた根拠を `note` に書く。
  - `hypothesis`（仮説）：資料から推測した関係。`note` に推測の根拠が必須。図では「［仮説］」と表示し、線を薄くする。
- 出典は財務データ JSON と同じ `"S2 p.5"` 形式。財務データ JSON の `sources`（S1 など）はそのまま参照できる。
  有報・企業サイトなど財務データ JSON にない資料は、ビジネスモデル JSON の `sources` に追加する（id は財務データ JSON と重ならない番号にする）。
  企業サイトのように頁番号がない資料は `"S5"` だけでよい。

## 2. ビジネスモデル JSON（`data/bizmodel/<決算期>.json`）

財務データ JSON（`data/<決算期>.json`）とは別のファイルにする（財務データの形式は変えない。`fin.py history` は `data/*.json` だけを読む）。
`bizmodel.py init --data <data.json> --out <data_dir>/bizmodel/<決算期>.json` で下書き（`draft: true`）を作る。

```json
{
  "schema": "fra-bizmodel", "schema_version": 1, "sample": true, "draft": false,
  "company": {"name": "サンプル情報サービス株式会社（架空）", "short_name": "サンプル情報（架空）", "code": "0000"},
  "period": "2027年3月期_第2四半期",
  "model_type": "btob_saas",
  "layout": {"split": "auto"},
  "sources": [{"id": "S4", "title": "【架空】有価証券報告書", "url": "https://example.com/yuho.pdf", "published": "2026-06-20", "kind": "有価証券報告書"}],
  "groups": [{"id": "saas", "name": "SaaS事業", "segment": "SaaS事業"}],
  "nodes": [
    {"id": "self", "name": "サンプル情報（架空）", "type": "company", "role": "self", "description": "業務ソフトのクラウド提供", "source": "S4 p.5"},
    {"id": "corp", "name": "法人顧客", "type": "company", "role": "customer", "groups": ["saas"],
     "description": "中小企業（個別の社名は資料に記載なし）", "source": "S2 p.6"}
  ],
  "edges": [
    {"from": "self", "to": "corp", "type": "service", "label": "クラウドサービスの提供", "source": "S2 p.6",
     "evidence_level": "fact", "group": "saas"},
    {"from": "corp", "to": "self", "type": "money", "label": "月額利用料", "source": "S2 p.6",
     "evidence_level": "interpretation", "note": "月額課金との記載から", "group": "saas"}
  ],
  "notes": []
}
```

### nodes（主体）

| キー | 内容 |
|---|---|
| `id` | 英小文字で始まる英小文字・数字・`_`（32字以内）。図の中の識別子 |
| `name` | 図に表示する名前。個別名が資料にない場合は一般名称 |
| `type` | アイコンの種類：`company`（企業・法人）、`person`（個人・消費者）、`people`（利用者・会員）、`worker`（人材・求職者・従業員）、`store`（店舗）、`factory`（工場・製造拠点）、`cloud`（クラウド・システム）、`government`（官公庁・自治体）、`financial`（金融機関・投資家）、`facility`（医療・介護・教育などの施設）、`device`（端末・機器）、`media`（メディア・広告媒体）、`business`（事業・部門）、`other` |
| `role` | 図の中の位置を決める役割：`self`（分析対象の会社。ちょうど1つ）、`group`（グループ会社・事業部門）、`supplier`（仕入先・委託先・供給側）、`channel`（販売チャネル・仲介）、`customer`（顧客）、`end_user`（顧客の先の利用者）、`partner`（提携先）、`investor`（株主・親会社・資金の出し手）、`other` |
| `description` | どのような主体か（表に表示） |
| `source` | 主体の存在を確認した出典（必須） |
| `groups` | 属する事業（`groups` の id のリスト。分割するときに使う） |
| `overview` | `true` なら、分割時の全社概要図にも入れる |

### edges（取引関係）

| キー | 内容 |
|---|---|
| `from` / `to` | 主体の id。**矢印の向きは流れの向き**（下表） |
| `type` | `service`（商品・サービス）、`money`（お金）、`information`（情報・データ）、`operation`（運営・委託）、`ownership`（所有・資本） |
| `label` | 矢印の説明（16字以内を推奨。図では2行まで折り返す。詳しい説明は `note`） |
| `source` | 関係を確認した出典（必須） |
| `evidence_level` | `fact` / `interpretation` / `hypothesis` |
| `note` | 解釈・仮説の根拠（`hypothesis` では必須） |
| `group` | 事業別の図に入れる場合の事業 id。省略すると全社概要図に入る |
| `overview` | `true` なら、`group` があっても全社概要図にも入れる |

| type | 色・線 | 矢印の向き |
|---|---|---|
| service（商品・サービス） | 青・実線 | 提供する側 → 受け取る側 |
| money（お金） | オレンジ・実線 | 支払う側 → 受け取る側 |
| information（情報・データ） | 紫・破線 | 送る側 → 受け取る側 |
| operation（運営・委託） | 緑・点線 | 業務を行う側（運営者・受託者）→ 運営される側・委託元 |
| ownership（所有・資本） | 灰・一点鎖線 | 出資する側（株主・親会社）→ 出資を受ける側 |

番号（①②…）は edges の順に付き、分割した図の間で共通。並べる順番は「主要な収益の流れ」から書くと読みやすい。

### model_type（事業モデルの型）

`btob_saas`、`btoc_platform`、`marketplace`、`manufacturing_wholesale`、`retail_food`、`staffing`、`advertising`、`finance`、`other`。
型は図の副題に表示し、配置に次のように使う。**取引関係は型から決めない（JSON が唯一の根拠）。**

- 両面型（`btoc_platform`・`marketplace`・`staffing`・`advertising`）：供給側（出店者・求職者など、`role: supplier`）を左、需要側を右、当社を中央に置き、供給側と需要側の直接の取引は当社を迂回して描く。
- 連鎖型（`manufacturing_wholesale`・`retail_food`）：仕入先と販売チャネルの段数を3段まで並べる（その他の型は2段）。

## 3. 配置（自動）

- 列：左から `supplier` → `self`・`group` → `channel` → `customer` → `end_user`。上段に `investor`、下段に `partner`・`other`。
  同じ側の主体の間に商品・サービスの流れがあれば、流れの向きに1列ずらす。
  当社が運営・所有する事業（`role: group`。当社から `operation` または `ownership` の矢印がある）が2つ以上あり、それぞれが当社と顧客・販売チャネルだけと取引している場合は、事業を当社と顧客の間の列に置く（当社 → 事業 → 顧客）。
- 列の中の並びは、つながる主体の縦位置の平均に近づける（交差を減らす）。当社は列の中央（上段とつながる場合は上端）。
- 2列以上離れた主体の間の矢印は、途中の列に通り道（ダミー）を確保して描く。
- 他の主体を通過する矢印は、直交の経路で迂回させる。同じ列の離れた主体への矢印は、交差が少ない側の辺から出す。
- 矢印の説明は、主体・他の説明と重ならず、他の矢印が説明の上を通らない位置に置く（線の上、線の両側、両側に少し離した位置から選ぶ）。
  主体・説明の重なりが解消できない場合は間隔を広げて再配置する（最大4回）。説明の上を他の矢印が通る箇所が残る場合も間隔を広げて減らすが、
  図が大きくなりすぎないように、重なり1か所を150pxと換算し、図の高さと既定の幅（820px）を超えた幅との合計が最小の間隔を選ぶ。残った箇所は警告として報告する。
- 主体が10を超えるか関係が16を超える場合は、全社概要図（`BM`）と事業別の詳細図（`BM-<groups の id>`）に分ける。
  そのため `groups` と、各関係の `group` を設定する。全社に共通する関係（親会社・事業の運営など）は `group` を付けない。
  事業の部門を主体（`role: group`、`type: business`）として置き、当社 → 事業（`operation`）でつなぐと全社概要図が読みやすい。

## 4. 図の構成

- 見出し（会社名・全社概要／事業名）、副題（決算期・型）
- 主体（アイコン＋名前。当社は青枠、グループ会社・事業は灰色の枠）と矢印（番号＋説明）
- 凡例（使った関係の種類、当社・グループの枠、［仮説］の意味）
- 出典の資料名と公表日

関係ごとの内容・根拠・出典の一覧表は、図にもノートにも入れない（ビジネスモデル JSON に残す）。ノートの「ビジネスモデル」の章には、図と `bizmodel.py table` の主体の表だけを貼り、図の説明文は書かない。

出力は編集用の `.drawio` と表示用の SVG（白背景・図のデータを埋め込み済み）。アイコンは SVG を図形のスタイルに埋め込んでいる（外部画像なし）。
矢印は主体に接続しているため、draw.io で主体を動かしても矢印は外れない。

## 5. 検証（build の結果に含まれる）

1. JSON：必須項目、id の形式と重複、`self` が1つ、存在しない主体への参照、`from` と `to` が同じ、種類の値、出典の有無と出典 id の存在、仮説の根拠、関係の重複、分割の上限
2. 図の構造：JSON のすべての主体と関係が図にあり、余分なものがない。各矢印の始点・終点の主体が JSON の `from`・`to` と一致（向き）、矢じりは終点側だけ、種類と色が一致、説明に番号がある
3. 配置：主体同士が重ならない、矢印が他の主体を通過しない、矢印の説明が主体に重ならない、説明の重複がない、凡例がある
4. 文字（diagrams.py と共通）：すべての文字が SVG に出力されている、文字同士が重ならない、キャンバスからはみ出さない、白背景
5. 矢印の交差の数と、説明の上を他の矢印が通る箇所は警告として報告する（エラーにはしない）

## 6. 失敗したとき

`bizmodel.py build`（`diagrams.py build` から自動で呼ばれる）は、失敗しても例外で止まらず、原因を `<決算期>_BM_figures.json` に記録する（`ok: false`、`stage`、`error`）。
財務諸表の図の結果（`diagrams.py build` の `ok`）には影響しない。

| 原因 | 直し方 |
|---|---|
| JSON の検証エラー（stage: validate） | エラーの内容どおりに JSON を直す（存在しない主体、出典の不足など） |
| 主体・関係が多すぎる | `groups` と `group` を設定して事業別に分ける。全社概要図に入る関係は `group` なし |
| 説明・矢印の重なり（stage: verify） | `label` を短くする（詳しい説明は `note`）。関係が集中する主体は事業別に分ける |
| draw.io がない | `brew install --cask drawio`（利用者の承認を得てから） |

直せない場合は、ノートの「ビジネスモデル」の章に図を作れなかったことと原因を書き、利用者に報告する。
`check_report.py` は生成失敗の記録を警告として出す（ビジネスモデル JSON がない場合はエラー）。
